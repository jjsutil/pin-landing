# roadmap-board

`planning/BOARD.md` is **generated, never hand-edited** (rule 7). The single source of
truth is issue frontmatter in `planning/issues/`.

## Status model and objective criteria

`status: backlog | ready | in-dev | review | staging | production`

- `ready` — the ERD/PRD/screen-spec files the issue references actually exist.
- `in-dev` — a branch named for the issue exists (`feat/I-003-*` etc.).
- `review` — a PR is open for that branch.
- `staging` — the PR merged.
- `production` — deployed or included in a release tag.

When regenerating, verify statuses against these criteria (branch list, `gh pr list`,
tags) and correct drift — the criteria win over whatever the frontmatter claims.

### Materialization for `source: github` repos (opt-in)

Repos that set `source: github` in the manifest keep the roadmap in GitHub Issues, not
in `planning/issues/` frontmatter — so there is nowhere to stamp `status:`. For those,
the same six-value model is materialized as **GitHub labels** when the manifest sets
`status_labels: true`:

- Labels `status:backlog | status:ready | status:in-dev | status:review | status:staging`
  (no `status:production` — a shipped issue is `closed`). At most one per issue.
- **Derived, not hand-set.** On regenerate, compute each open issue's status from the
  objective criteria via `gh`: an open PR that references the issue → `status:review`; a
  branch named for it but no PR → `status:in-dev`; otherwise its stated `status:*` label
  or `status:backlog`. A merged/closing PR closes the issue (rule 10) — closed is the
  terminal state, no label needed. Reconcile drift: strip a stale `status:*` and apply
  the derived one.
- The BOARD groups by these labels; the label is the SSoT of intermediate state, GitHub
  open/closed is the SSoT of done. When `status_labels` is unset/false, the repo uses
  bare open/closed only (the pre-existing behavior) and the BOARD shows a single open
  table — never invent labels a repo didn't opt into.

## Classification criteria (declared here, applied by issue-writer)

- `impact: high` — touches a core user flow, unblocks other issues, or is user-visible.
- `cost: high` — large diff surface, new dependencies, or migration/infra risk.
- Otherwise `low`. Every classification carries a one-line rationale **in the issue
  body** (issue-writer writes it; flag issues missing it).

## BOARD.md structure

1. Header comment: `<!-- GENERATED by roadmap-board — do not hand-edit -->` + timestamp.
2. One table per status (id, title, type, impact, cost, epic, age).
3. **2×2 impact/cost matrix** — quick wins (high impact / low cost) highlighted first.
4. **Cost projection line** — the one-liner produced by cost-guard from COSTS.md.
5. **Staleness alerts** — defaults: `in-dev` >14 days without commits on its branch,
   `review` >7 days without PR movement. Thresholds are tunable via the manifest in
   `.claude/repo-conventions.md` (`staleness_in_dev_days`, `staleness_review_days`).

## README executive summary

Regenerate **only** the region between `<!-- BOARD-SUMMARY:START -->` and
`<!-- BOARD-SUMMARY:END -->` in README.md: counts per status, top 3 quick wins, the cost
projection line, and a link to BOARD.md. Touch nothing outside the markers.

## Transitions triggered by other skills

- `pr-writer` → sets the linked issue to `review`, then calls this skill.
- Merge → `staging`; release tag → `production`.
- `issue-writer` → new issue lands, board regenerates.

## First run (backfill)

Issues without frontmatter: add the schema, classify with rationale, infer status from
the objective criteria. Then generate the first BOARD.md and README summary block
(create the markers if absent, at the end of the README's intro section).
